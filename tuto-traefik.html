Introduction

De quoi parle-t-on ?

Quand on lance plusieurs applications dans des conteneurs, chacune veut son port.

Très vite, on se retrouve avec localhost:3000, localhost:4444, localhost:8080...

Le reverse proxy organise : une seule porte d'entrée, des adresses lisibles, et les applications cachées derrière.

  • Proxy — un intermédiaire placé du côté du client.
  • Reverse proxy — un intermédiaire placé du côté du serveur, qui reçoit les visiteurs et les aiguille vers la bonne application.
  • Traefik — un reverse proxy qui découvre tout seul les conteneurs Docker et crée les routes correspondantes, sans fichier de configuration à recharger.

Module 2

Un proxy (ou forward proxy)

Un intermédiaire placé du côté du client. Au lieu de contacter directement un site, le client demande au proxy d'y aller à sa place.

Qui le met en place ?

L'organisation qui possède les clients : une entreprise, une école, un fournisseur d'accès.

À quoi ça sert ?
  • filtrer les sites autorisés
  • garder en cache les pages consultées souvent
  • masquer l'identité des postes (un VPN relève de la même logique)
  • journaliser les accès sortants
À retenir : le proxy connaît les clients et travaille pour eux. Le serveur de destination, lui, ignore tout de leur existence.
Module 2

Un reverse proxy (« proxy inverse »)

Un intermédiaire placé du côté du serveur. Les visiteurs croient parler au site ; en réalité ils parlent au reverse proxy, qui transmet à l'application appropriée.

Qui le met en place ?

Celui qui héberge les applications.

Exemples

Traefik, nginx, HAProxy, Caddy.

À retenir : le reverse proxy connaît les serveurs et travaille pour eux. Le visiteur, lui, ignore tout de ce qu'il y a derrière.
Module 2

La différence, en une phrase

Le proxy protège et dessert le client ; le reverse proxy protège et expose le serveur.

Techniquement, les deux font la même chose — relayer une requête HTTP. Ce qui change, c'est de quel côté ils sont placés et pour qui ils travaillent.

Placé du côtédu clientdu serveur

Module 2

Pourquoi utiliser un reverse proxy ?

a • Une seule porte d'entrée

Un seul port ouvert au lieu d'un par service. Toute la surveillance, la journalisation et le filtrage se font au même endroit.

b • Des adresses lisibles

app.localhost plutôt que localhost:3333. Personne n'a à mémoriser de numéros de ports.

c • Les applications restent cachées

Les conteneurs n'exposent aucun port : ils sont totalement injoignables depuis l'extérieur. Réduire la surface exposée est un principe de sécurité fondamental.

d • Fin des problèmes de CORS

En exposant l'API sous app.localhost/api, tout se passe en même origine : le problème disparaît sans une ligne de configuration côté application.

e • Les préoccupations transverses sont mutualisées

HTTPS, authentification, limitation de débit, compression, redirections : traités une fois dans le reverse proxy, au lieu d'être réimplémentés dans chaque service.

f • La répartition de charge

Plusieurs exemplaires d'un service peuvent se cacher derrière une même adresse, le reverse proxy distribuant les requêtes.

Module 3

Router — « cette requête est-elle pour moi ? »

Une règle d'aiguillage. Elle examine la requête et décide si elle la prend en charge.

Les règles les plus courantes

RègleCorrespond à
Host(`app.localhost`)le nom de domaine demandé — le port est ignoré
PathPrefix(`/api`)les URL commençant par /api
Path(`/health`)exactement cette URL
Method(`GET`)la méthode HTTP
Header(`X-Cle`, `valeur`)la présence d'un en-tête

Elles se combinent avec && (et), || (ou) et ! (non).

Quand plusieurs règles correspondent, Traefik retient la plus longue, donc la plus spécifique. C'est pourquoi Host(`app.localhost`) && PathPrefix(`/api`) l'emporte sur Host(`app.localhost`) sans qu'on ait à intervenir.
Module 3

Service et Middleware

Service — « où j'envoie »

La destination : le conteneur et son port interne.

Ce numéro est toujours celui sur lequel l'application écoute dans le conteneur — jamais un port publié sur la machine. Se tromper ici produit un 502 Bad Gateway.

Le mot loadbalancer est là même avec un seul conteneur : Traefik répartit automatiquement si plusieurs exemplaires du même service existent.

Middleware — « ce qui se passe entre les deux »

  • stripprefix retire un préfixe d'URL. Le navigateur demande /api/health, l'API reçoit /health. Sans lui, l'API répondrait 404 puisqu'elle n'expose pas de route /api/health.
  • basicauth exige un identifiant et un mot de passe avant de laisser passer. C'est ce qui protège le dashboard.

Il en existe une trentaine : redirections, compression, limitation de débit, ajout d'en-têtes, liste d'adresses autorisées… Un routeur peut en enchaîner plusieurs, appliqués dans l'ordre déclaré.

Module 3

Le réseau Docker

Dans notre cas tous les services partagent le réseau tuto-traefik-net, un couloir privé dans lequel les conteneurs se joignent par leur nom de service, sans qu'aucun port ne soit publié.

  1. Traefik peut joindre api:8000 alors que ce port n'est publié nulle part. Le seul port visible de la machine est le 1111.
  2. Un service absent de ce réseau est invisible pour Traefik. C'est la cause la plus fréquente d'erreur 404 dans l'exercice.

Cette option indique à Traefik quelle adresse utiliser lorsqu'un conteneur appartient à plusieurs réseaux. Sans elle : des erreurs aléatoires, difficiles à diagnostiquer.

Module 3

Les labels et la découverte automatique

Un label est une simple étiquette clé=valeur attachée à un conteneur. Docker n'en fait rien : ce sont des métadonnées. Mais Traefik, lui, les lit.

C'est ce qui rend cette configuration si particulière : elle ne vit pas dans un fichier de configuration de Traefik, mais sur les conteneurs eux-mêmes. Chaque service transporte sa propre description de routage.

Configuration STATIQUE

Les options de démarrage de Traefik (--entrypoints, --providers). Les changer impose de redémarrer Traefik.

Configuration DYNAMIQUE

Les labels des autres conteneurs. Relus en permanence, à chaud, sans redémarrage.

Piège rencontré en préparant ce tutoriel. Les noms de routers et de services sont globaux : ils ne sont pas cloisonnés par projet Compose. Deux projets qui nomment tous deux un routeur api entrent en collision. La parade, déjà en place :
--providers.docker.constraints=Label(`com.docker.compose.project`,`tuto-traefik`)

Le réflexe, avant tout

Traefik ne plante presque jamais : il démarre, puis ignore silencieusement ce qu'il ne comprend pas. Les logs sont donc la première source de vérité.

Deuxième source de vérité : les routes que Traefik connaît réellement.

Si votre route n'apparaît pas ici, inutile de chercher côté navigateur : Traefik ne la connaît pas.

Troisième source, complémentaire : les logs d'accès(--accesslog=true), ils disent ce qui est réellement arrivé à chaque requête, là où les routes ne disent que ce que Traefik sait faire.

Accessible via docker compose logs api, docker compose logs frontend, docker compose logs hello.

Une ligne par requête. RouterName/ServiceName disent qui a traité la requête, DownstreamStatus ce que l'application a répondu, Duration le temps pris (en nanosecondes).

Sécurité

Le socket Docker : le compromis central

C'est cette ligne qui permet toute la magie de la découverte automatique. C'est aussi le point le plus sensible de l'architecture.

Le socket Docker est l'interface de commande du moteur Docker. Y avoir accès, c'est pouvoir créer des conteneurs — et un conteneur peut monter n'importe quel répertoire de la machine. Un accès au socket Docker équivaut donc en pratique à un accès administrateur à la machine hôte. Le :ro limite l'accès à la lecture, ce qui réduit le risque sans le supprimer.

Pour un tutoriel local, c'est parfaitement acceptable. En production, trois approches plus sûres :

  1. Un proxy de socket Docker (par exemple tecnativa/docker-socket-proxy) placé devant, qui ne laisse passer que les requêtes de consultation dont Traefik a besoin.
  2. Le provider « file » : la configuration est écrite dans un fichier YAML, et Traefik n'a plus besoin d'accéder à Docker. On perd la découverte automatique.
  3. Un socket en mode « rootless », ou l'API Docker exposée en TLS avec des certificats clients.
À retenir : la découverte automatique n'est pas gratuite, elle se paie en privilèges accordés au reverse proxy.
Sécurité

Ce projet n'est pas une configuration de production

Trois points le distinguent d'un déploiement réel :

  1. Le socket Docker est monté dans Traefik. C'est ce qui permet la découverte automatique, mais cela équivaut en pratique à un accès administrateur.
  2. Aucun HTTPS. Tout est en clair, sur HTTP.
  3. Le mot de passe du dashboard est demo, et il est versionné dans le dépôt.

Le dashboard est en revanche protégé par authentification, et non exposé via --api.insecure — cette variante figure en commentaire dans le compose, précisément pour expliquer pourquoi on l'évite.

Ce que ferait une vraie production

HTTPS automatique

Traefik obtient et renouvelle les certificats Let's Encrypt tout seul, et les applications continuent de ne parler qu'en HTTP en interne. C'est l'un de ses grands arguments.

Point de défaillance unique

Oui, Traefik en est un. En production, on en fait tourner plusieurs exemplaires derrière un répartiteur de charge. C'est le compromis assumé de toute architecture à point d'entrée unique.

« nginx fait la même chose, non ? » Oui, et très bien. La différence est la découverte automatique : avec nginx, ajouter un service impose d'éditer un fichier de configuration et de recharger le serveur.
FAQ

Les questions qui reviennent

« Pourquoi le port 1111 et pas 80 ? »

Parce que 80 est souvent déjà pris et qu'en dessous de 1024 il faut des droits administrateur. En production, ce serait 80 et 443. Le numéro est un choix de configuration, pas une règle.

« Est-ce que .localhost marche partout ? »

Sur la plupart des systèmes oui, tout *.localhost pointe automatiquement vers la machine locale. Sous Windows, il faut parfois éditer le fichier hosts. Le DNS ne sert qu'à trouver la machine ; c'est l'en-tête HTTP Host que Traefik examine, ce que démontre :

« Et le HTTPS ? »

Module 8 • Question 1

Où Traefik sert, aujourd'hui

Traefik est né en 2015 d'un constat : dans une infrastructure de conteneurs, les adresses changent tout le temps. Un proxy dont la configuration dort dans un fichier à recharger n'y suffit plus.

TerrainCe qu'il y apporte
Docker Compose, homelab, auto-hébergementle cas de ce tutoriel — le meilleur rapport bénéfice/effort
KubernetesIngress Controller, et surtout la Gateway API qui remplace Ingress
Préproductions éphémères en CIune route par branche, créée et détruite avec le conteneur
SaaS multi-locataires, edgeroutage par Host, certificat wildcard par DNS-01
Passerelle d'APIrate-limit, authentification déléguée, WAF — sans toucher au code
Passerelle IAdevant des modèles et des serveurs MCP écran suivant
Ce qu'il ne fait pas, et qu'on croit souvent : il ne sert pas de fichiers statiques (aucune directive root — d'où le nginx de ce projet), il n'est pas un maillage de services (Istio, Linkerd), et il n'est pas le plus rapide (Go plutôt que C).

Module 8 • Question 2

Remède 1 — le cookie collant

Traefik open source sait épingler un client sur une réplique : il lui pose un cookie, le relit à chaque requête, et le ramène au même endroit.

La limite, et elle est sérieuse. Ceci suppose un client qui gère les cookies. Un navigateur, oui. Un agent écrit en Python avec httpx.post() ou requests.post() sans session persistante, non — il ignore le cookie et reste cassé.
Module 8 • Question 2

Remède 2 — l'affinité sans cookie

Plutôt que de marquer le client, on calcule sa destination à partir de son adresse IP :

StratégieComportementAffinité
wrr (défaut)round-robin pondéréaucune
p2cdeux serveurs tirés au sort, le moins chargé gagneaucune
hrwhachage consistant sur l'IP du clientpar IP
leasttimele plus rapide à répondreaucune

Consistant a un sens précis : si une réplique disparaît, seuls ses clients sont redistribués — là où un IP modulo 3 rebattrait tout le monde.

La limite, symétrique. L'affinité tient à l'adresse IP, pas au client. Deux agents derrière un même NAT partagent une IP : même réplique, équilibrage dégradé.

Module 8 • Question 2

Répliquer ne suffit pas : et si l'une meurt ?

L'affinité règle le problème des sessions. Elle ne dit rien d'un autre, plus banal : Traefik ne vérifie rien par défaut. Tant que le conteneur tourne, il reste dans la répartition — même s'il ne rend plus aucun service.

Un conteneur vivant peut très bien être mort : base injoignable, thread bloqué, mémoire saturée. Et restart: unless-stopped ne le relèvera pas, puisqu'il n'est pas tombé.
Une réplique sur trois est en panne12 requêtes
sans sonde — Traefik continue de la servir8/12 — une sur trois échoue, au hasard
avec sonde — retirée du pool en 3 s12/12 — personne n'a rien vu

À ne pas confondre avec le healthcheck: de Docker Compose : celui de Docker décide si le conteneur est sain, celui de Traefik s'il reste dans le pool. Seul le second influence le routage.

Module 8 • Question 2

Le streaming derrière un proxy

Toute IA générative diffuse au fil de l'eau. Un proxy est un intermédiaire, et un intermédiaire peut accumuler avant de retransmettre. Un seul middleware suffit à tout annuler.

La même API, la même routeMorceaux reçusPremier morceau
sans middleware160,25 s
avec buffering13,75 s
La durée totale est identique : le serveur a travaillé aussi vite. C'est l'attente perçue qui change du tout au tout — écran vide pendant quatre secondes, puis tout d'un coup.

Le piège : on ajoute buffering pour une raison sans rapport — plafonner la taille des documents téléversés vers l'IA (maxRequestBodyBytes) — sans réaliser qu'on vient de mettre les réponses en tampon du même coup.

Module 8 • Question 2

Deux idées reçues, démenties par la mesure

Elles circulent partout. Le script les met en défaut sous vos yeux, sur traefik:v3.6.

« Jamais compress sur du SSE »

Vrai pour nginx. Faux ici.

  • le flux est compressé — Content-Encoding: gzip ;
  • et les jetons arrivent quand même un par un ;
  • le compresseur de Traefik transmet au fil de l'eau.

Un héritage nginx recopié de billet en billet, sans jamais être revérifié.

« Il faut flushInterval=-1 »

Inutile dans la quasi-totalité des cas.

  • Traefik est bâti sur le proxy inverse de Go ;
  • celui-ci transmet immédiatement, en ignorant le réglage, dès que la réponse n'annonce pas sa longueur ;
  • c'est le cas de tout vrai flux (chunked).
La démonstration le prouve dans les deux sens : un service réglé à flushInterval=5s laisse passer /stream sans le moindre retard, mais accumule tout pendant 4 s sur /stream-fixe — la seule route à annoncer un Content-Length.

À retenir : si un streaming est saccadé derrière Traefik, ce n'est presque jamais flushInterval qu'il faut aller changer. Le streaming ne se configure pas — il se préserve.

Module 8 • Question 3

À quoi comparer Traefik

Opposer « Traefik et nginx » n'a qu'à moitié de sens : ils ne visent pas le même problème. Trois familles se distinguent.

1 · Proxies classiques

Configuration écrite à la main, rechargée explicitement.

  • nginx — omniprésent, rapide, sert le statique
  • HAProxy — la référence du load-balancing
  • Caddy — HTTPS automatique, config minimale

2 · Cloud-native

Configuration déduite de l'état du cluster. La famille de Traefik.

  • Traefik — Docker et Kubernetes
  • Envoy — le moteur d'Istio, très verbeux
  • Istio / Linkerd — maillage complet

3 · Passerelles d'API et services gérés

Kong, Tyk, APISIX — cycle de vie des API : clés, quotas, portail développeur. AWS ALB, Azure App Gateway — zéro exploitation, adhérence au fournisseur. Cloudflare Tunnel — expose sans ouvrir de port : complémentaire, pas concurrent.

Module 8 • Question 4

Caddy ou Traefik ?

Tous deux en Go, binaire unique, HTTPS automatique. Ils divergent sur l'origine de la configuration — et tout le reste en découle.

Caddy — ses avantages

  • un site en HTTPS tient en deux lignes
  • HTTPS automatique y compris en local (CA interne)
  • sert les fichiers statiques
  • excellent hors Docker, sur une VM classique

Ses inconvénients

  • pas de découverte Docker en standard (plugin tiers caddy-docker-proxy)
  • quasi absent de Kubernetes
  • ajouter un plugin impose de recompiler (xcaddy)

Traefik — ses avantages

  • découverte automatique native (Docker, K8s, Consul, Nomad)
  • middlewares chaînables et réutilisables
  • Ingress + Gateway API, TCP/UDP
  • dashboard, Prometheus, OpenTelemetry d'origine

Ses inconvénients

  • labels verbeux, quatre notions avant la première route
  • ruptures v1→v2→v3, documentation mouvante
  • ne sert pas le statique ; socket Docker à assumer
  • WAF, AI et MCP Gateway réservés à Hub (payant)

Module 8 • Question 5

Les deux réglages à ne pas remettre à plus tard

ratelimit — la première protection devant une IA

Une requête vers un modèle coûte des secondes de GPU. Sans limite, un script parti en boucle suffit à saturer le service pour tout le monde. À poser avant même l'authentification.

Mesuré : 200 200 200 puis 429 429 429… — l'application n'a jamais vu les requêtes refusées.

Le HTTPS, et un second provider

Un certificat n'appartient à aucun conteneur : il est global. Aucun label Docker ne peut le déclarer — c'est là que le provider file devient indispensable.

Les deux providers tournent en même temps et leurs configurations fusionnent — le dashboard affiche « Docker » et « File ». C'est aussi la réponse à la question de sécurité du module 6 : on peut se passer du socket Docker, en décrivant tout dans des fichiers. On y perd la découverte automatique, on y gagne de ne plus monter le socket.
Module 8 • Question 5

Quand le routage ne suffit plus : headers

Rappel — CORS est une règle imposée par le navigateur : une page chargée depuis une origine (domaine + port + protocole) ne peut pas appeler par défaut une API sur une autre origine, sauf si le serveur appelé l'autorise explicitement via des en-têtes Access-Control-*.

Le module 2 a résolu ce problème par le routage : même origine, donc plus de CORS du tout. Mais ce n'est pas toujours possible — une application mobile, un widget embarqué chez un tiers, une API consommée depuis un autre domaine. Dans ces cas, c'est Traefik lui-même qui répond aux en-têtes CORS, via le middleware headers :

Le même middleware headers sert aussi, hors de tout contexte CORS, à poser des en-têtes de sécurité (Strict-Transport-Security, X-Frame-Options…) sur toutes les réponses d'un routeur.
Le même-origine (module 2) reste la solution par défaut, la plus simple et la plus sûre. headers est un correctif pour les cas où on ne maîtrise pas les deux origines.
Module 8 • Question 5

forwardauth — l'auth déléguée

basicauth protège le dashboard avec un couple identifiant/mot de passe. Mais un vrai projet a son propre système d'authentification (JWT, session, OAuth) — le réécrire dans chaque service à protéger ne passe pas à l'échelle.

forwardauth inverse le problème : avant de transmettre la requête, Traefik interroge un service d'authentification avec les mêmes en-têtes. Une réponse 2xx laisse passer la requête (enrichie des en-têtes renvoyés par le service d'auth, ex. X-User-Id) ; sinon, Traefik renvoie directement l'erreur du service d'auth, sans jamais atteindre le service protégé.

C'est l'équivalent open source de ce que Traefik Hub vend comme « OAuth 2.1 en resource server » pour le MCP Gateway, vu plus haut dans ce module : la logique est identique, seulement moins packagée.
Le service d'auth devient un point de passage obligé pour chaque requête protégée : sa latence et sa disponibilité deviennent critiques pour tout ce qu'il protège.
Module 8 • Bonus

Ce que Traefik mesure de lui-même

Chaque service applicatif peut déjà exposer ses propres métriques — un endpoint /metrics côté FastAPI, par exemple. Traefik peut en plus exposer les siennes : une vue côté bord, complémentaire à la vue applicative.

Métrique applicationMétrique Traefik
durée d'une inférence, taille du contexte…latence totale perçue par le client, requêtes par router/service, codes retour, retries

Les deux se complètent, aucune ne remplace l'autre : l'application sait ce qu'elle a fait, Traefik sait ce que le client a vécu.

Le tracing distribué (OpenTelemetry) suit le même principe pour reconstituer le trajet d'une requête à travers plusieurs services.
